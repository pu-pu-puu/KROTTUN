# Exploration notes: diagnostics and proxy controls

Scope: read-only exploration for phase 3; no implementation or application launch. Sources read: `AGENTS.md`, `.autopilot/PROGRESS.md`, README recovery/limitations, `gui/app_webview.py`, `gui/web/index.html`, `core/proxy_model.py`, `core/storage.py`, `core/protection_session.py`, `core/singbox_manager.py`, `core/ip_service.py`, relevant tests, and `tools/host-validation/proxy_failover.py`.

## Operational constraints and product facts

- Do not launch `main.py` or perform live WFP, TUN, firewall, proxy-setting or other real-network changes. README says protection persists through stop/errors/exit; removal requires explicit recovery. VM packet capture/release readiness remains an open acceptance item. See `AGENTS.md` and README section “Защита и соединения — проверка перед выпуском”.
- The Windows Internet Settings system proxy is read-only inspected by the app. `ProxyEnable` being set produces a warning; never modify the user's configured proxy. README says it can interfere with TUN and browser hostname visibility.
- External IP refresh is already constrained: `get_current_system_ip()` uses HTTPS api.ipify.org, `requests.Session.trust_env=False`, no redirects, 3-second request bound. `_refresh_ip_async()` only runs with a healthy protected TUN or when explicitly unarmed/IDLE; protected mode validates lifecycle/session context, coalesces pending calls and applies a 4-second UI deadline. Do not add a direct internet probe while protection is armed.
- HTTPS is not decrypted. Hostnames in the connection log are observed SNI/HTTP Host when present; IP-only is honest. Snapshot logging can miss short sessions. DNS is handled by sing-box while protected; UDP is denied by policy and domain proxy endpoints require a cached hostname-bound numeric endpoint during policy.
- `ProxyItem` and `proxies.dat` contain credentials. `ProxyItem.to_dict()` includes the password, so do not serialize it into diagnostics, JS, logs or notes. `_proxy_to_dict()` is deliberately safe (does not include password/raw line); UI uses `copy_proxy_by_id()` to copy the secret through backend-only clipboard path.

## Current bridge/API, synchronization, persistence

`gui/app_webview.py:ProxyTunBridgeApi` owns an `RLock` (`_lock`) for fast state/list changes, `_op_lock` for serialized heavy start/stop/release, `TunState` state, `ProtectionSession`, and a bounded geo `ThreadPoolExecutor(max_workers=4)`. Long lifecycle transitions run on daemon worker threads and use operation generation/cancel state. Keep diagnostics outside lifecycle locks while probing; snapshot immutable/copy inputs under `_lock`, then re-check generation/state before publishing results. If concurrent diagnosis calls are possible, use a single-flight gate and generation to reject stale results.

Existing methods:

- `get_state()` returns selected/active proxy via safe `_proxy_to_dict`, list, system IP, protection state and read-only `network_warning`.
- `select_proxy(proxy_id)` persists selected identity only in memory; if currently RUNNING and selection changes, it starts `_do_toggle("start", generation)` (protected reconnect).
- `add_proxy(host, port, protocol, username, password)` validates host/port/protocol, supports `auto` protocol via `probe_proxy_protocol(... timeout=1.5)`, saves with rollback through `_save()`, asynchronously determines geo.
- `delete_proxy(proxy_id)` persists with rollback, chooses first remaining on selected deletion. UI rejects deleting the active node while connected.
- `_save()` delegates to `save_proxies(self.proxies)`. `storage.save_proxies()` serializes all fields then DPAPI-encrypts; write is atomic and synchronized. `settings.json` uses `save_setting`; it is not encrypted. Existing settings default `bypass_telegram=False` and the bridge forces it false.
- `ping_proxy()` and `ping_all()` deliberately refuse background/direct checks while protection is not `unarmed`. Ping is only TCP connect reachability, not an HTTPS/application-level proxy test. The all variant spawns its own executor and currently has no global single-flight coordination.
- `_network_warning()` reads only current user's `Internet Settings\ProxyEnable` and caches for 10 sec; it never returns configured endpoint.
- `_refresh_ip_async()` uses `_ip_context()`, tied to `ProtectionSession.generation`, manager process and reachability while protected. Refresh result is suppressed if context changes. Existing tests: `tests/test_ip_journal_fix.py`, `tests/test_lifecycle_bounds.py`.

`ProtectionSession.connect(proxies)` takes an ordered iterable, snapshots candidates (copies each `ProxyItem`), resolves hostnames only while unprotected under a 15-second aggregate DNS deadline / 3-second per-host cap and 4-slot bounded semaphore, then arms deny-only policy before sequential attempts. Between attempts it backs off (up to 30 seconds). It arms exact proxy endpoint, starts sing-box and waits for reachability; failures stop core, re-arm deny-only and proceed. It returns success on first verified tunnel; exhausted list remains blocked. `_do_toggle("start")` currently constructs candidates as `[selected] + every other proxy in UI list order`; user cannot exclude candidates or edit order independently. That implicit fallback is the behavior to replace if phase requires a deliberate ordered/excludable list. Keep `ProtectionSession`'s protected retry/recovery guarantees.

## Safe reuse for one-button network diagnosis

Useful primitives:

- `core.ip_service.get_current_system_ip(timeout=...)`: HTTPS + `trust_env=False`, but only through `_refresh_ip_async`'s valid route context. It does not return exit IP on active proxy unless system routing is through protected TUN. Result contains address and should be shown only if intended; never write it to diagnostic logs/report.
- `core.ip_service.quick_ping_proxy(proxy, timeout=...)`: bounded TCP socket to proxy endpoint (does DNS in caller socket path); changes `ProxyItem.latency_ms/last_status`.
- `core.ip_service.test_proxy(proxy, timeout=...)`: existing HTTPS via proxy using requests, but passes credentials in proxy URL, uses environment defaults (unlike hardened `get_current_system_ip`), can then make a second geo request with independent 3 sec timeout and no single aggregate deadline. Not safe to reuse unchanged for a strict one-button diagnosis: refactor a new single-session helper with `trust_env=False`, `allow_redirects=False`, no geo lookup, quote credentials, one monotonic overall deadline and bounded response body; return sanitized categorical facts only.
- `core.singbox_manager._probe_request()` performs HTTPS health checks with trust_env false and exact status/body validation. `_probe_tunnel()` isolates probes in a killable spawn worker, guarded by per-manager gate/generation and ownership retained until confirmed exit (AGENTS requirement). If validation is performed while TUN is running, reuse protected path/its health state; do not run independent direct HTTPS/DNS probes that might bypass the TUN. The probe currently means “tunnel HTTPS health responded,” not proof every system app uses it.
- `probe_proxy_protocol()` is a TCP protocol-handshake detector for adding a proxy, not full DNS/HTTPS diagnosis.

Suggested result contract: `run_diagnostics(proxy_id: str | None) -> {success, run_id, started_at, completed_at, checks:[{id,state,summary,elapsed_ms}], system_proxy:{enabled: bool|None}}`. Keep check IDs/states fixed; no exception text, credentials, URLs, IPs, endpoint hostnames, registry configured endpoint or raw packet data in diagnostics. Distinguish `skipped` from `failed` and `unknown` (for checks unsafe/unavailable in current protection state). Consider checks: selected proxy TCP endpoint reachability; proxy DNS availability/hostname-bound result; authenticated HTTPS request through selected proxy (only when safe in current mode); protected TUN health; routed external-IP check only through an explicitly valid route context; read-only Windows system proxy enabled warning. Define clearly whether “DNS” is the proxy-host resolution or tunneled public DNS; they prove different things and must not be merged. UI may show precise local classifications, not claim leak-proof operation. Single global diagnostic worker / cancellation or run generation avoids accumulated calls and late status; keep a hard overall deadline and per-stage deadlines. If Python's synchronous DNS can linger in a thread, isolate it with the existing killable worker pattern or daemon + bounded gate; don't assume socket timeout bounds getaddrinfo.

## Edit existing proxy

- No `edit_proxy` backend API exists. Add one that takes ID plus edited fields, validates like `add_proxy`, keeps the same ID and unrelated metadata, and commits through `_save()` with rollback on failure. Never return password. For a blank password field in edit UI, preserve existing password; make clearing password an explicit action to avoid accidental credential loss.
- If target is the currently active proxy (or tunnel is RUNNING/STARTING/STOPPING/blocked), safest default is reject/defer the edit rather than mutate endpoints underneath armed WFP/session snapshots. Otherwise endpoint/credentials changes should take effect on next explicit connect; avoid automatic restart without clear current lifecycle behavior. Existing delete UI already prohibits active-proxy deletion. Review selection/fallback references when ID is retained.
- Edit UI can reuse `modalAdd` as mode `add|edit`, prefill safe host/port/protocol/username, never prefill password; invoke distinct `edit_proxy(id, ...)`. Host/user values must be assigned with `.value`, not markup string templates.

## Explicit ordered/excludable fallback list

- Current proxy list is ordered by insertion and also implicitly defines fallback order after selected. There is no per-proxy enabled/excluded field or dedicated fallback editor. `selected_proxy_id` is not persisted. `proxies.dat` preserves `ProxyItem` list order and is DPAPI protected.
- Suggested explicit settings: persist ordered fallback IDs (e.g. `fallback_proxy_ids: list[str]`) and/or explicit `fallback_enabled` IDs; do not persist credential copies. Validate on load against current proxy IDs, remove duplicates/stale IDs; decide default migration once (e.g. current list order) and thereafter honor explicit selection. IDs stay stable on edit; deletion removes ID from sequence, addition should be opted in or appended per an explicit product decision. A dedicated ordering/edit UI should support up/down and include/exclude toggles without changing selected server or running TUN.
- Change `_do_toggle` to snapshot chosen IDs under `_lock` and produce candidate objects in exact explicit order; ensure primary selection semantics are intentional (either selected always first when included, or list order exclusively). User-requested exclusions must never be silently re-added by a “selected + all others” fallback. Pass immutable tuple to `ProtectionSession.connect`; it already snapshots each candidate for safe protected lifecycle and records per-proxy failover journal events.
- Add tests for migration/default order, stable ordering and ID retention across edits, excluding selected/backup entries, stale IDs/deletion cleanup, snapshot behavior when UI mutates during connect, and that exclusions don't reach `ProtectionSession.connect`.
