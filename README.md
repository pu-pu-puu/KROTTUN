## ⚡ О проекте

**KROTTUN** перехватывает весь сетевой трафик операционной системы на 3-м сетевом уровне (IP-пакеты) с помощью виртуального сетевого адаптера Wintun и прозрачно маршрутизирует его через указанный SOCKS5 или HTTP прокси.

В отличие от стандартных системных прокси Windows (WinINet), которые игнорируются мессенджерами, консольными утилитами и играми:
* **Весь стек приложений** (браузеры, Telegram, Discord, Git, curl, Steam, игры) начинает работать через прокси без необходимости настраивать каждое приложение отдельно.
* **Никаких утечек DNS или IPv6**: встроенный резолвер перенаправляет все DNS-запросы в шифрованные DoH (Cloudflare / Google) с трехуровневым failover, а IPv6-утечки на dual-stack сетях блокируются.
* **Геолокация узлов и флаги стран**: автоматическое фоновое определение страны и города по IP/домену с визуальным отображением флагов в списке серверов.
* **Интеллектуальный автодетект протоколов**: неблокирующее параллельное зондирование сокетов (SOCKS5 / HTTP CONNECT) со строгой RFC-валидацией.
* **Фирменный Glassmorphism интерфейс**: обновленные модальные окна, замер пинга в реальном времени и телеметрия трафика.

## 🚀 Быстрый старт

### Требования
* Windows 10 (версия 1809+) или Windows 11 (64-bit).
* Установленный компонент **Microsoft Edge WebView2 Runtime** (входит в стандартную поставку Windows 10/11).
* Права **Администратора** (требуются Windows для создания виртуального сетевого адаптера Wintun и настройки маршрутов).

---

### Запуск из исходного кода

1. Клонируйте репозиторий:
   ```bash
   git clone https://github.com/pu-pu-puu/KROTTUN.git
   cd krottun
   ```

2. Установите зависимости:
   ```bash
   pip install -r requirements.txt
   ```

3. Запустите приложение с правами Администратора:
   ```bash
   python main.py
   # или используйте скрипт:
   run.bat
   ```

---

### Сборка автономного .exe (PyInstaller)

Для сборки одного независимого `.exe` файла со всеми зависимостями и иконкой:

```bash
pyinstaller KROTTUN.spec --noconfirm
```

Готовый файл появится в каталоге `dist\KROTTUN.exe`. Он содержит встроенный манифест администратора (`uac_admin=True`) и запускается в один клик.

## 📋 Форматы добавления прокси

KROTTUN поддерживает как одиночное добавление через форму, так и пакетный импорт списка прокси в любом из следующих форматов:

```text
# 1. IP:PORT:USER:PASS
192.0.2.1:1080:username:password

# 2. IP:PORT (без авторизации)
192.0.2.2:8080

# 3. SOCKS5 URL
socks5://username:password@192.0.2.3:1080

# 4. HTTP / HTTPS URL
http://username:password@192.0.2.4:8080
```

## Защита и соединения — проверка перед выпуском

Новый WebView-путь устанавливает собственные WFP-фильтры IPv4/IPv6 до запуска
TUN. Проверяется нативное чтение установленных условий. Защита постоянная:
обычное отключение, ошибки и закрытие приложения её не снимают. Список резервных
серверов фиксируется; каждая попытка выполняется последовательно, с задержкой.
После истощения списка нужен ручной повтор. Кнопка подключения во время попытки
отменяет последующие попытки. Текущая проверка/запуск имеет ограниченный таймаут.

Снять блокировку: **«Отключить защиту и вернуть интернет»**. Сначала завершается
ядро, затем удаляются только фильтры KROTTUN. После сбоя закройте приложение и
из повышенного PowerShell в каталоге проекта выполните:

```powershell
python -m core.kill_switch --release
```

Команда завершает sing-box из доверенного каталога KROTTUN и удаляет только
собственную политику; остальные правила Windows остаются. Машинный файл
`%ProgramData%\ProxyTUN\protection-recovery.json` содержит идентификатор политики
и числовые адреса для восстановления. Паролей в нём нет. После перезапуска
сохранённая блокировка распознаётся; доменные серверы без кэшированного адреса
пропускаются с записью события. Неизвестное состояние не считается защищённым.

Прямые исключения Telegram, xray, AG и LAN отключены. В этом режиме UDP
отклоняется: SOCKS UDP relay может назначить новый адрес/порт, для которого нет
проверенного разрешения. DNS обслуживается ядром через прокси. Блокировка может
мешать DHCP и сетевому входу после перезагрузки: для восстановления предусмотрено
явное снятие защиты. Первичное разрешение имён серверов происходит **до** защиты;
защита начинается после успешной установки WFP, не при открытии приложения.

После подтверждённой остановки старого процесса новый запуск получает имя
`sing-tun-<UUID>`: повторное имя после аварии может конфликтовать с оставшимся
нативным GUID Wintun. Readiness, скорость и WFP используют текущий интерфейс,
WFP разрешает только его точный LUID. Старые и чужие адаптеры не удаляются.

Вкладка «Соединения»: максимум 1000 строк в памяти, фильтр, пауза отображения,
очистка. Источник — авторизованный loopback Clash API и события жизненного цикла.
Поиск процессов ядром включён для журналирования даже без process routing rules.
Имена сайтов берутся из наблюдаемого HTTP Host/TLS SNI, когда приложение их
передаёт. Sniff выполняется до обработки DNS; IP назначения не подменяется,
HTTPS не расшифровывается, тела запросов не сохраняются. Поздно появившееся имя
обновляет существующую строку. Если браузер сам использует внешний прокси или
приложение не передаёт имя, журнал честно показывает только наблюдаемый IP.
Предупреждение о системном прокси читает лишь флаг Windows; программа его не
отключает. Внешний IP проверяется одним HTTPS-запросом без наследования системного
прокси только через здоровый защищённый TUN (либо явно снятую защиту). Проверка
имеет отдельный четырёхсекундный срок UI; поздний ответ сменившейся сессии не
показывается, параллельные сетевые проверки не накапливаются.
Снимки могут пропускать короткие соединения; недоступный источник обозначается
отдельно. Неизвестные программа/маршрут не угадываются. Тела, конфигурация,
credentials и URL query не сохраняются. История очищается при закрытии.

**Это ещё не доказанная защита от утечек и не готовность к выпуску.** Unit-тесты
с fake backend и `sing-box check` подтверждают логику и схему, но не поведение
Windows. Не запускались реальные WFP/TUN изменения на рабочем компьютере.
Требуется изолированная Windows VM и packet capture: новые/существующие TCP/UDP,
входящие инициированные потоки, IPv4/IPv6/DNS, LAN/loopback forwarder, смена
адаптера, broad Allow чужого firewall, авария ядра/GUI/прокси, перезагрузка и
восстановление. ALE policy change переавторизует существующие потоки; возврат
transaction commit не считается доказанным барьером для уже летящих пакетов.
Отдельные BOOTTIME deny-фильтры предусмотрены для старта TCP/IP; переход к
persistent-политике и поведение при остановке/сбое BFE ещё требуют проверки.
Схема `/connections` проверяется адаптером при чтении; совместимость ответа
поставляемого ядра должна быть подтверждена в VM. Постоянные фильтры используют
NULL provider и собственный sublayer, чтобы не зависеть от активации provider
без Windows-службы. Установленные фильтры не означают проверенную передачу пакетов.

Первичные основания: [слои и условия WFP](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-conditions-available-at-each-filtering-layer),
[переавторизация ALE](https://learn.microsoft.com/en-us/windows/win32/fwp/ale-re-authorization),
[время жизни объектов](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management).


## Редактирование серверов, резервы и диагностика

В строке сервера доступно редактирование: название, адрес, порт, SOCKS5/HTTP,
логин и новый пароль. Сохранённый пароль в форму не загружается: пустое поле
сохраняет его, отдельный флаг удаляет. При ошибке записи введённые поля остаются.
Правка во время работы туннеля применяется при следующем подключении; текущий
сервер и снимок резервов не меняются. В переходном состоянии дождитесь завершения.

Окно «Резервы» позволяет включать, исключать и переставлять серверы. Основной
выбранный сервер всегда идёт первым. Пустая очередь означает работу без резервов:
после отказа интернет остаётся заблокирован. До первого явного сохранения действует
прежний порядок всех серверов. После сохранения новые серверы автоматически не
включаются. При ручном подключении фиксируется очередь; автоматические повторы
используют только её оставшуюся часть. Правки относятся к следующему подключению.

Кнопка «Диагностика подключения» показывает пять отдельных результатов: прокси /
туннель, DNS, HTTPS, внешний IP и флаг системного прокси Windows. Проверка ничего
не подключает и не снимает защиту. При здоровом защищённом TUN DNS проверяется
системным getaddrinfo для example.com, HTTPS и IP — по системной маршрутизации
без наследования proxy environment. При снятой защите, IDLE и остановленном ядре
проверяется только выбранный сервер: TCP-доступность endpoint, DNS через фиксированный
DoH-запрос через этот прокси, HTTPS и IP через тот же явный транспорт. TCP-успех
не подтверждает авторизацию; DoH-успех не является проверкой системного DNS.
При блокировке, неизвестном состоянии, переходе или отсутствии выбранного сервера
сетевые строки пропускаются. Прямого запасного запроса при ошибке прокси нет.

Сетевые операции выполняются одним дочерним процессом spawn, привязанным к Windows
Job до разрешения запросов. Бюджет операций — 10,5 секунды плюс ограниченное
подтверждение остановки; UI завершает ожидание не позднее 12 секунд, включая
зависший вызов моста. Неподтверждённый выход процесса блокирует новые проверки.
Перед снятием защиты приложение подтверждает выход процесса диагностики; если выход
не подтверждён, защита сохраняется. Смена сервера, редактирование выбранной записи,
остановка, release или закрытие
отменяют устаревший результат. Закрытие диалога прекращает опрос и отменяет проверку.
Результаты хранятся только в памяти; валидированный IP показывается в диалоге,
не пишется в журнал. Настройки системного прокси не меняются: включённый флаг даёт
предупреждение, ошибка чтения — честный пропуск. Таймаут не доказывает утечку.
Эта диагностика не заменяет незавершённую VM/IPv6/DNS/reboot-приёмку защиты.

Изолированная проверка production HTML (fake bridge, все внешние запросы браузера
запрещены): `node prototypes/proxy-controls/verify.cjs`. Скриншоты находятся рядом.
Приложение и EXE при этой проверке не запускаются.

## Ручной замер узлов

«Проверить пинг» и «Замерить все» доступны при снятой защите и остановленном
ядре либо при здоровом защищённом TUN. При снятой защите измеряется TCP-соединение
напрямую. При защите активный узел определяется по реально работающему серверу
ядра, даже если выбран другой. Для него измеряется **HTTPS через активный туннель**:
время до ответа 204 от фиксированного https://cp.cloudflare.com/generate_204
по маршрутизации ОС, без системного прокси окружения и без перенаправлений.
При неудаче разрешена ещё одна HTTPS-проверка www.gstatic.com/generate_204
по тому же маршруту и в общем восьмисекундном бюджете. Показанная задержка —
время только успешной HTTPS-попытки; неудачная попытка расходует общий срок,
но не увеличивает показанное значение. HTTP и прямого fallback нет.
Подключения активного прокси к его собственному endpoint для замера нет.
Это задержка HTTPS через работающий туннель, а не прямой ping до сервера.
Неудачная проверка означает «Нет замера»; она не меняет здоровье ядра,
не запускает failover и не доказывает недоступность прокси.

Для остальных узлов при защите измеряется **отклик протокола через TUN**:
SOCKS5/HTTP по текущему маршруту ОС. Локального подтверждения TCP недостаточно;
проверка ждёт ответ прокси без передачи сохранённых credentials. Ответ об
обязательной авторизации тоже подтверждает отклик, но не проверяет пароль.
Этот замер включает текущий туннель и не является прямой задержкой до endpoint.
Режим (tcp, tun или tun_https) сохраняется вместе с результатом и показан
в подсказке значка задержки. Предыдущий неудачный замер адреса активного узла
через него самого после обновления показывается как «Нет замера» до повторной
проверки; записанные задержка и здоровье не подменяются.

При блокировке, неизвестном или переходном состоянии запрос отклоняется.
Новых WFP-исключений и прямого запасного транспорта нет. Совпадающий кэш
hostname используется как числовой endpoint; прочие имена разрешаются только
в здоровом TUN. Неответивший резервный узел обозначается таймаутом, не начатый
до общего срока — непроверенным. Один дочерний процесс, до восьми задач,
восемь секунд на весь замер и до 0,9 секунды на завершение процесса.
Перед снятием защиты его выход должен быть подтверждён. Повторные запросы
не накапливаются.
